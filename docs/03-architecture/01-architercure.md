## 1. Разделение на сервисы

### Принцип деления

1. **По юзкейсам (бизнес-возможностям)** — определяет, *какие* сервисы выделить.
2. **По нефункциональным требованиям** — объясняет, *почему* их держать отдельно.


### Сервисы

| Сервис               | Юзкейсы                                                                                                                                     | Акторы                           | Данные                        |
|----------------------|---------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------|-------------------------------|
| **link-service**     | UC-1 Создать ссылку<br>UC-2 Создать пачку<br>UC-5 Статистика (вход и проверка создателя)<br>UC-6 Удалить ссылку<br>UC-8 Очистить устаревшие | Пользователь, Партнёр, Создатель | **Владелец** ссылок           |
| **redirect-service** | UC-3 Перейти по ссылке<br>UC-4 Зайти роботом                                                                                                | Посетитель, Робот                | Только **читает** ссылки      |
| **stats-service**    | UC-7 Учесть переход<br>UC-5 Статистика (данные)                                                                                             | Система                          | **Владелец** счётчиков кликов |

### Почему отдельно: разные нефункциональные профили

|             | link-service       | redirect-service           | stats-service       |
|-------------|--------------------|----------------------------|---------------------|
| Нагрузка    | ~10/с, пик сотни/с | ~1 000/с, пик **10 000/с** | ~1 000 событий/с    |
| Скорость    | < 500 мс           | **< 50 мс (p99)**          | отставание — минуты |
| Доступность | 99,9%              | **99,99%**                 | может отставать     |

- redirect-service масштабируется независимо от остальных.
- Сбой создания ссылок или статистики **не задевает** редирект (NFR-4.1).

### Общая схема (черновик)

```
   Пользователь / Партнёр                         Посетитель / Робот
            │                                             │
            ↓                                             ↓
   ┌─────────────────┐                          ┌──────────────────┐
   │  link-service   │                          │ redirect-service │
   └───┬─────────┬───┘                          └───┬──────────┬───┘
       │ пишет   │ запрос статистики          читает│          │ событие перехода
       ↓         ↓                                  ↓          ↓
  ┌──────────┐  ┌───────────────┐              ┌───────┐   ┌───────┐
  │ Postgres │  │ stats-service │ ←─────────── │ Redis │   │ Kafka │
  │ (ссылки) │  │ (счётчики)    │   события    └───┬───┘   └───┬───┘
  └────▲─────┘  └───────────────┘   из Kafka       │ промах    │
       └───────────────────────────────────────────┘           │
                                     stats-service читает ←────┘
```

### Хранилище ссылок: компромисс

- Для начала link-service и redirect-service используют **один Postgres**.
- Это антипаттерн **Shared Database**, принят осознанно:
    - пишет только link-service, redirect-service — только `SELECT` (отдельный пользователь БД);
    - таблица одна, схема простая и стабильная;
    - полная развязка через события даёт задержку, которая конфликтует с NFR-5.1
      («новая ссылка работает сразу»).
- **Развитие:** redirect-service переходит на read-реплику, затем — на своё хранилище,
  синхронизируемое событиями из link-service, с запасным запросом к источнику при промахе.

### Межсервисное взаимодействие

| Откуда           | Куда          | Как               | Зачем                                  |
|------------------|---------------|-------------------|----------------------------------------|
| redirect-service | stats-service | Kafka, асинхронно | Учёт перехода, без ожидания            |
| link-service     | stats-service | HTTP, синхронно   | Получить число переходов для создателя |
