# P-01. Мгновенная инвалидация кэша при удалении ссылки

**Проблема:** [P-01](00-problems.md#p-01) — удалённая ссылка ещё до 10 секунд работает из кэша.
**Статус:** Принято · **Затрагивает:** link-service, redirect-service

## Идея

При удалении link-service публикует событие `LinkDeleted`, redirect-service получает его
и удаляет ключ ссылки из Redis.

## Главная сложность — когда отправлять событие

Удаление пишется в базу, событие — в Kafka. Две системы нельзя изменить одной атомарной
операцией (**проблема двойной записи**).

| Когда отправлять | Что сломается                                                                 |
|------------------|-------------------------------------------------------------------------------|
| До коммита       | Коммит упал → ссылка жива, а из кэша уже удалена; событие о том, чего не было |
| После коммита    | Сервис упал между коммитом и отправкой → событие потеряно, кэш грязный        |
| Kafka недоступна | Либо отказывать в удалении, либо терять событие                               |

## Решение — Transactional Outbox

```
DELETE /api/links/{code}
  └─ транзакция: links.deleted_at + outbox_messages (PENDING)
                         │
          OutboxSendJob, раз в секунду
                         ↓
               Kafka, топик link-events
                         ↓
     redirect-service: LinkEventConsumer → DEL link:{code}
```

1. В **той же транзакции**, что и удаление, событие пишется в таблицу `outbox_messages`.
   Коммит — есть и удаление, и событие. Откат — нет ни того, ни другого.
2. Фоновая задача раз в секунду отправляет неотправленные события в Kafka и помечает их
   отправленными. Kafka недоступна — события ждут в таблице.
3. redirect-service читает топик `link-events` и удаляет ссылку из Redis.

## link-service

**Таблица `outbox_messages`** — общая для любых событий, не только удаления:

| Колонка                                     | Зачем                                |
|---------------------------------------------|--------------------------------------|
| `aggregate_type`, `aggregate_id`            | Чьё событие: `link`, `42`            |
| `event_type`                                | Тип события: `LinkDeleted`           |
| `payload` (jsonb)                           | Само событие в JSON                  |
| `status`                                    | `PENDING` → `PUBLISHED` или `FAILED` |
| `attempts`, `next_attempt_at`, `last_error` | Повторы при сбоях                    |

**Компоненты:**

| Класс                 | Что делает                                                 |
|-----------------------|------------------------------------------------------------|
| `OutboxWriter`        | Сохраняет событие в транзакции вызывающего кода            |
| `OutboxSendJob`       | Раз в секунду запускает отправку                           |
| `OutboxKafkaSender`   | Берёт до 100 готовых событий, отправляет, обновляет статус |
| `KafkaEventPublisher` | Отправляет в Kafka и ждёт подтверждения до 5 секунд        |
| `OutboxCleanupJob`    | Раз в сутки (03:30) удаляет отправленные события           |

**Как событие ложится в Kafka:**

| Kafka              | Откуда                       | Зачем                                               |
|--------------------|------------------------------|-----------------------------------------------------|
| топик              | `aggregate_type` + `-events` | `link-events`                                       |
| key                | `aggregate_id` (id ссылки)   | События одной ссылки — в одной партиции, по порядку |
| value              | `payload`                    | Тело события                                        |
| header `eventType` | `event_type`                 | Консьюмер понимает тип, не разбирая JSON            |
| header `eventId`   | `id` строки outbox           | Для отсева дублей, если понадобится                 |

**Сбои отправки:** пауза растёт 1 → 2 → 4 … до 60 секунд; после 10 неудач событие
получает статус `FAILED` и больше не отправляется.

Продюсер: `acks=all`, идемпотентность включена — Kafka подтверждает запись только после
сохранения на всех репликах и не пишет повтор дважды.

## redirect-service

- `LinkEventConsumer` (группа `redirect-service`) читает `link-events`, пропускает события
  с другим `eventType` и удаляет `link:{code}` из Redis.
- Битый JSON — ошибка в лог, событие пропускается: повтор не поможет.
- Redis недоступен — ошибка не глушится, событие повторяется с паузой 1 → 2 → 4 … 30 секунд,
  **не дольше 5 минут**. Дольше смысла нет: к этому времени запись истечёт по TTL.
- TTL кэша — **5 минут** (было 10 секунд).

## Гарантии

- Доставка «хотя бы один раз»: событие может прийти дважды — повторный `DEL` безопасен.
- Обычно удалённая ссылка перестаёт работать через **1–2 секунды**.
- При любых сбоях доставки — не позже чем через **5 минут** (TTL).
- TTL больше не отвечает за скорость удаления, поэтому его подняли с 10 секунд до 5 минут:
  в базу ходим в 30 раз реже.

## Ограничения

- ⚠️ **Редкая гонка:** запрос прочитал ссылку из базы до коммита удаления, а положил в кэш
  уже после того, как событие обработано, — ссылка проживёт до конца TTL.
- Сейчас link-service работает в одном экземпляре. Для нескольких события нужно брать
  через `FOR UPDATE SKIP LOCKED`, чтобы экземпляры не отправляли одно и то же.
- События со статусом `FAILED` никто не переотправляет — их видно только в таблице.
